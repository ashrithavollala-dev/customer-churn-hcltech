# Customer Churn Prediction and Retention Prioritization

**Live demo:** https://customer-churn-prediction-hcl.streamlit.app
The project gives each customer a probability of churning in the next 30 days. It explains which signals
drive that estimate and builds a ranked list of customers for a retention team to review. The review
threshold and capacity can be changed without retraining. The work includes:

- a chronological train / validation / test pipeline comparing a Dummy baseline, Logistic Regression and CatBoost
- probability calibration, capacity (top-K) and lift analysis, and segmented error analysis
- SHAP explanations, both global and per customer
- a FastAPI backend and a Streamlit dashboard that use the same inference code

## 3. Churn definition and data

- **Prediction point:** `snapshot_date`, always a month end. Every feature describes the customer up to that date.
- **Horizon:** the following 30 days.
- **Target:** `churn_next_30d` = 1 if the customer churned within 30 days after the snapshot.
- **Eligible customer:** a customer who is active at the snapshot date and has one row in the snapshot file.
  Rows sent to the API or uploaded to the dashboard must have valid values for all 24 model features;
  otherwise they are rejected with an explanation, not scored. Only `last_csat_score` may be missing.
- **Observation windows:** the features use 1-, 3- and 6-month look-backs (usage m1 to m3, tickets, late
  payments and disputes in the last 6 months, login recency).

| Split | Snapshots | Rows | Churners | Churn rate |
|---|---|---|---|---|
| Train | Jan - Aug 2025 | 665 | 151 | 22.7% |
| Validation | Sep - Oct 2025 | 172 | 43 | 25.0% |
| Test | Nov - Dec 2025 | 183 | 32 | 17.5% |

The splits are used exactly as provided and are never reshuffled. Every customer appears once in the whole
dataset, so the same customer cannot appear in both training and test. There are no missing values or
duplicate rows in the final files. Full checks are in `reports/data_validation_report.md`.

### Features (24)

Feature selection was already done before this repository, on training data only. 29 engineered features
were built from the raw columns. Features with |correlation| >= 0.9 to another feature, and rare features,
were removed. L1 logistic regression with TimeSeriesSplit cross-validation on train then kept 24. This
project uses exactly those 24 and does not re-select features on validation or test.

- Numeric (18): `usage_change_pct_m3_to_m1`, `billing_risk`, `service_pain_score`, `inactive_flag`,
  `unpaid_amount_6m`, `stickiness`, `price_hike_flag`, `discount_pct`, `resolution_rate`, `days_since_login`,
  `bill_unpaid_flag`, `billing_disputes_last_6m`, `charge_change_pct_3m`, `renewal_due_60d`,
  `support_tickets_m1`, `net_charge`, `support_tickets_m3`, `last_csat_score`
- Categorical (6): `contract_type`, `tenure_band`, `region`, `paperless_billing`, `payment_method`,
  `acquisition_channel`

`customer_id`, `snapshot_date` and the target are never model inputs. The ID and date are kept for reporting.

### How the engineered features were verified

`src/data_validation.py` rebuilds the engineered features from `data/raw/customer_churn_raw_1050.csv`. The
raw file is used only for this check; nothing is trained on it.

| Feature | Rebuilt rule | Match |
|---|---|---|
| `billing_risk` | late payments (6m) + billing disputes (6m) | 100% |
| `stickiness` | add-on services + autopay + non-monthly contract | 100% |
| `service_pain_score` | 2 x complaints (90d) + unresolved tickets (90d) + (CSAT <= 2) | 100% |
| `usage_change_pct_m3_to_m1` | (usage m1 - usage m3) / (usage m3 + 1) x 100 | 97.5% (25 rows differ; 20 had missing raw m3) |
| `resolution_rate` | resolved / tickets, 1.0 when there are no tickets | 100% |
| `inactive_flag` | days since login > 30 | 100% |
| `bill_unpaid_flag` | no last payment date recorded | 100% |
| `renewal_due_60d` | contract end date within 60 days of the snapshot | 100% |
| `unpaid_amount_6m`, `days_since_login`, `Unknown` region/channel | as named | 100% |

### Leakage controls

- None of the raw date fields (last login, last payment, bill due date, signup) is later than `snapshot_date`.
- No single feature separates churners suspiciously well. The highest single-feature ROC-AUC on train is 0.749
  (`usage_change_pct_m3_to_m1`), well below what a copy of the label would give.
- Imputation, scaling and encoding are fitted inside the model pipeline on **train only**.
- Validation is used for hyperparameters, model choice, calibration and the threshold. The test set is read
  by one script (`src/evaluate.py`) after the model bundle has been saved.
- `renewal_due_60d` uses the contract end date. That is a known contract term at the snapshot, not a
  future event.

## 4. Method

### Models (`src/train.py`)

| Model | Setup | Tuning grid (chosen on validation) |
|---|---|---|
| Dummy | `strategy="prior"` - always predicts the training churn rate | none |
| Logistic Regression | median imputation + `StandardScaler` for numbers, `OneHotEncoder(handle_unknown="ignore")` for categories, L2 penalty | `C` in {0.01, 0.03, 0.1, 0.3, 1}, `class_weight` in {None, balanced} |
| CatBoost | native categorical handling, learning rate 0.03, shallow trees | `depth` in {3, 4, 5}, `l2_leaf_reg` in {3, 10}, `iterations` in {200, 500} |

There is no SMOTE or oversampling. Class imbalance is handled through `class_weight` as one of the tuned
options. All random seeds are 42.

**Selection rule:** within each family, the best configuration is the one with the highest validation PR-AUC,
with ties broken by top-20% churn capture. CatBoost replaces Logistic Regression only if it is better by more
than 0.02 PR-AUC **and** captures at least as many churners in the top 20%. Otherwise the simpler, more
transparent model is kept. The validation set is small, so even this 22-run search (10 LR + 12 CatBoost) may overfit it a little.

### Calibration (`src/calibration.py`)

1. The selected model is trained on train and then frozen.
2. A sigmoid (Platt) calibrator is fitted on that model's **validation** predictions.
3. To check whether it helps, the calibrator is fitted on 4/5 of validation and scored on the remaining 1/5.
   This is repeated 5 times, so the improvement is never measured on rows the calibrator was fitted on.
4. Calibration is applied only if this cross-validated Brier score is lower than the raw Brier score.

Result: raw validation Brier 0.155 and cross-validated calibrated Brier 0.129, so calibration was applied.
The raw model overestimated churn (mean prediction 0.39 against an observed rate of 0.25) because it was
trained with balanced class weights. On test, the Brier score improves from 0.131 to 0.091. Test churn (17.5%)
is lower than validation churn (25%), so the calibrated model still slightly over-predicts on test (mean 0.227).
See `reports/test_calibration_table.csv`. Calibration is monotonic, so ranking metrics (PR-AUC, ROC-AUC,
top-K) do not change.

### Operating threshold

0.44 is the threshold that maximises F1 on the calibrated validation probabilities. The dashboard lets users
pick any threshold or capacity, and `reports/*threshold_tradeoff.csv` lists flagged volume, TP, FP and FN
from 0.05 to 0.95.

### Risk categories

- **High:** probability >= the operating threshold (0.44).
- **Medium:** >= the training churn rate (0.227).
- **Low:** below the training churn rate.

### Explainability (`src/explain.py`)

`shap.LinearExplainer` is used for the selected Logistic Regression, with a background of 200 training rows.
`shap.TreeExplainer` is used if CatBoost is ever selected; a test confirms this path also works. SHAP values
for the one-hot columns of a categorical feature are summed back into that one feature.

- Values are in **log-odds of the raw (uncalibrated) model**: base value + contributions = raw log-odds. A
  test checks this to 1e-6. They are **not** percentage-point changes in the calibrated probability.
- Global: mean |SHAP| ranking and a beeswarm plot (`reports/figures/shap_*`).
- Local: a waterfall plot and contribution table for any customer ID, plus a short summary generated from the
  SHAP table. No explanation text is written by hand.
- SHAP describes what the model relies on. It does not show what causes churn.

### Metrics used

| Metric | What it tells you |
|---|---|
| PR-AUC (average precision) | Ranking quality for the churn class; main metric because churn is the minority class. A no-skill model scores the churn rate (about 0.2). |
| ROC-AUC | Probability that a random churner is ranked above a random non-churner. Secondary, because it looks optimistic under imbalance. |
| Precision | Of the customers flagged, the share who actually churned. Low precision means wasted outreach. |
| Recall (churn capture) | Of all churners, the share that was flagged. |
| F1 | Harmonic mean of precision and recall at one threshold. |
| Precision@K / Recall@K / Lift@K | The same measures when only the K highest-risk customers can be reviewed. Lift = precision@K / overall churn rate. |
| Cumulative gain | Share of churners captured as more of the ranked list is reviewed. |
| Brier score | Mean squared error of the probabilities (lower is better); measures calibration and sharpness together. |
| Reliability diagram | Mean predicted against observed churn rate in 5 equal-size bins. |

## 5. Setup and running (Windows cmd)

Requires **Python 3.11**. Run all commands from the repository root.

```cmd
py -3.11 -m venv venv
venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### Run the pipeline (in this order)

```cmd
python -m src.data_validation   :: data checks -> reports\data_validation_report.md, EDA tables
python -m src.train             :: train, tune on validation, select, calibrate, threshold -> models\churn_model_bundle.joblib
python -m src.evaluate          :: ONE-TIME test evaluation -> reports\test_*.csv, figures
python -m src.explain           :: SHAP global/local outputs -> reports\shap_*.csv, figures
python -m src.prioritize        :: retention queue for the latest period -> reports\retention_queue.csv
```

`src.train` takes about 2 minutes on a laptop, mostly for the CatBoost grid. The other steps take a few
seconds each.

### Notebooks (raw data -> modelling files)

The notebooks in `notebooks/` show how the raw file became the modelling files. They are saved with all
outputs and charts, so they can be read on GitHub without running anything. Run them **in this order**, because
each one reads the output of the previous one:

| # | Notebook | What it does | Writes |
|---|---|---|---|

| 2 | `02_eda.ipynb` | Churn rate overall, over time and by segment; churned vs stayed for numeric columns; behaviour-change warning signs; correlation heatmap; single-feature ROC-AUC; data-quality notes; key insights linked to features. | `reports/figures/eda_*.png` |
| 3 | `03_feature_engineering_selection.ipynb` | Builds about 40 engineered features, selects features on train (correlation filter, rare-feature filter, L1 logistic regression with `TimeSeriesSplit(4)`), compares the result with the 24 features in use, rebuilds the final tables and checks them against `data/*_final.csv` column by column. | `data/processed/{train,validation,test}_rebuilt.csv` |

```cmd

```

If Jupyter starts a kernel from another Python installation (for example a "No module named seaborn" error),

- `reports/cleaning_log.csv` lists every cleaning step with the number of rows/values affected, the action and

  cells overall, target 100%). The only differences are 5 validation/test values of `usage_change_pct_m3_to_m1`
  for customers whose raw `usage_hours_m1` was negative. The notebook uses the absolute value; the original
  files replaced those values with `usage_hours_m2`. No training row differs. Notebook 3 also shows that the
  20 missing raw `usage_hours_m3` values were filled from `usage_hours_m2`.

### Start the API

```cmd
uvicorn api:app --reload --port 8000
```

- Swagger docs: http://127.0.0.1:8000/docs
- `GET /health` returns the model name, threshold, whether calibration is applied, and the feature list.
- `POST /predict` takes one customer (the 24 features, `customer_id` optional) and returns the probability,

## 8. Limitations and unresolved data issues

1. **Small evaluation sets.** Validation has 43 churners and test has 32. The test PR-AUC 95% CI is 0.58 to 0.86.
2. **One validation set does several jobs.** It is used for tuning, model choice, calibration and the
   threshold. A larger dataset would allow a separate calibration period, such as the last month of train held
   out chronologically.
3. **Short-tenure history.** 21 customers (13 train, 6 validation, 2 test) have under 90 days' tenure but
   usage recorded three months back, before signup. This is a generator artefact. The rows are kept unchanged.
   `tenure_days` is not in the final files, so this can only be seen in the raw file.
4. **CSAT imputation.** 45 missing and 4 out-of-range (0, 7, 9) CSAT scores were set to 4.0. That is the
   median over the full raw file, which happens to equal the train-only median. There is no "CSAT missing"
   flag, so imputed and real 4.0 scores look the same to the model.
5. **Features that cannot be fully rebuilt.** Five `usage_change_pct_m3_to_m1` values do not match the
   reconstructed formula, and the imputation for the 20 rows with missing raw `usage_hours_m3` is not
   recorded. The original feature-generation code is needed to confirm these. The rows were left as provided.
6. **One snapshot per customer.** Each customer appears once, so there is no within-customer history and
   no test of repeated scoring.
7. **Drift.** Test churn (17.5%) is lower than validation churn (25%), so calibrated probabilities run slightly
   high on test. In practice the calibrator should be refitted on recent labelled data.
8. **Small segments.** Segments with fewer than 30 customers or 5 churners are marked in
   `reports/test_segment_performance.csv`. Examples are Two-year contracts, the 0-6m tenure band, the North
   and West regions, and Cash payers.
9. **Fairness.** No protected characteristics are in the data. `region` is a geographic field and could act as
    a proxy in real data, so it should be reviewed before real-world use.
10. **Decision support only.** The tool ranks customers for human review. It makes no retention, pricing or
    contract decisions and does not show that anyone was retained.
